# Snapshot — v2.52.0: pgxpool health endpoint

Single-chunk cycle. Operators under load need visibility
into DB pool pressure (acquire latency, exhaustion,
construction backlog). v2.52 adds an endpoint that
exposes the pgxpool runtime stats.

## REST

```
GET /api/v1/health/pool
```

Response:
```json
{
  "schema": "api:v1",
  "data": {
    "pool": {
      "acquire_count": 1234,
      "acquire_duration_ns": 5000000,
      "acquired_conns": 3,
      "canceled_acquire_count": 0,
      "constructing_conns": 0,
      "empty_acquire_count": 0,
      "idle_conns": 7,
      "max_conns": 10,
      "total_conns": 10,
      "new_conns_count": 12,
      "max_lifetime_destroy_count": 0,
      "max_idle_destroy_count": 0
    },
    "timestamp": "2026-05-17T..."
  }
}
```

503 when no pool configured (memory-mode deployments).

## Adapter pattern

`handlers.PoolStat` is a flat struct mirroring the
relevant fields from `pgxpool.Stat`. `handlers.PoolStatter`
interface requires only `Stat() *PoolStat` — this lets the
handlers package stay free of pgxpool imports. cmd_serve
adapts the real `*pgxpool.Pool.Stat()` into this shape
via a thin wrapper.

## APIV1Deps

  - New field `PoolStatter PoolStatter` (optional).
