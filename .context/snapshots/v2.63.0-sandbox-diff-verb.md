# Snapshot — v2.63.0: `elsereno sandbox diff` subverb

Single-chunk cycle. Adds the `diff` subverb to the
read-only `elsereno sandbox` tree built in v2.62 — the
exact vNext follow-up flagged in the v2.62 snapshot's
"Honest scope" (`elsereno sandbox diff A B` → symmetric
difference of two profile schemes).

## Why now

v2.62 exposed `list` + `introspect`, letting operators
dump a single profile's .sb Scheme. The natural next
question during a security audit is comparative: *"what
does `exploit` allow that `scan` does NOT?"* Eyeballing two
full Scheme dumps is error-prone; `diff` answers it
directly and machine-readably.

## Verb

### `elsereno sandbox diff PROFILE_A PROFILE_B [--json]`

Line-level set difference + intersection between two .sb
Schemes. Comparison is done after trimming whitespace per
line, so multi-line clauses are compared as their own
lines — operators get a fast, deterministic answer without
a structured Scheme-clause parser.

Text mode prints a unified-style report with a header
naming both profiles, a count line, and `+`/`-` prefixes
(`-` = only in A, `+` = only in B):

```
$ elsereno sandbox diff exploit scan
# diff sandbox profiles: A=exploit  B=scan
# common=N  only_in_a=N  only_in_b=N
- (allow ipc-posix-shm)
+ (deny file-write*)
```

JSON mode emits a stable, sorted shape:

```
$ elsereno sandbox diff exploit scan --json
{"a":"exploit","b":"scan",
 "only_in_a":[...],"only_in_b":[...],"common":[...]}
```

All three arrays are sorted lexicographically so the
output is deterministic across runs (operators piping to
`git diff` of two captures need stable ordering). `common`
is included so the comparison can be sanity-checked.

## Platform

Reuses the v2.62 `schemeForProfile()` accessor, so the
cgo/non-cgo split is inherited — no new build-tagged files.
On darwin+cgo the real Schemes are diffed; on every other
offensive build the verb exits with a clear "schemes
unavailable (need darwin+cgo)" error rather than silently
returning an all-empty diff (the failure mode that would
otherwise mislead an auditor into thinking two profiles are
equivalent).

Profile names are validated at the args layer via
`Profile.Valid()` before any scheme lookup — a bogus name
fails with a hint to `elsereno sandbox list`.

## Implementation

All in the existing `cmd_sandbox_offensive.go`
(`//go:build offensive`):

  - `newSandboxDiffCmd()` — cobra wiring, `--json` flag,
    `cobra.ExactArgs(2)`. Registered via
    `cmd.AddCommand(newSandboxDiffCmd())` in the existing
    `newSandboxCmd()`.
  - `sandboxDiffResult` — JSON shape
    (`a`/`b`/`only_in_a`/`only_in_b`/`common`).
  - `runSandboxDiff()` — validates profiles, fetches both
    schemes, guards the unavailable-build case, renders
    text or JSON.
  - `diffSchemes()` — pure set difference + intersection,
    sorted output.
  - `schemeLineSet()` — splits a Scheme into a set of
    trimmed, non-empty lines.

## Test coverage (4 new, both build paths)

  - `TestSandboxDiff_TwoProfilesJSON` — `diff exploit scan
    --json` populates a/b + the three arrays; asserts
    `ipc-posix-shm` is exploit-only, `deny file-write*` is
    scan-only, `(version 1)` is common. On non-cgo builds
    asserts the "schemes unavailable" error instead.
  - `TestSandboxDiff_SelfDiffEmpty` — `diff dial dial`
    yields empty only_in_* arrays + non-empty common
    (determinism + trim sanity check). Skipped on non-cgo.
  - `TestSandboxDiff_UnknownProfile` — bogus name fails at
    the args layer with "unknown profile".
  - `TestDiffSchemes_LineLevel` — pure unit test of
    `diffSchemes()` (no cobra): whitespace-only lines
    dropped, lines trimmed before compare, intersection +
    symmetric difference correct.

All pass on both cgo and non-cgo offensive builds.

## Honest scope

  - Line-level, not clause-level. Reordered-but-equivalent
    clauses, or semantically-equal-but-textually-different
    Schemes, are reported as differences. A structured
    Scheme parser would be more precise but is overkill for
    the audit use case; deferred.
  - darwin+cgo only, same as `introspect`. No Linux
    seccomp-bpf diff (cBPF blobs need a disassembler pass —
    same vague-future caveat as v2.62).
  - No build-size change: ~150 LoC of new code in an
    existing file, no new deps.
