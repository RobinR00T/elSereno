# Snapshot — v2.45.0: /runs ?since= / ?until= time-window filter

Single-chunk cycle. Closes v2.22 + v2.46 prerequisite. The
v2.13 sparkline shows bucket-level data; v2.45 lets the
dashboard drill-down by clicking a bucket → opens runs
filtered to that bucket's window. Backend filter lands now;
UI click-handler lands v2.46.

## REST

```
GET /api/v1/schedules/{id}/runs?since=2026-05-17T08:00:00Z&until=2026-05-17T09:00:00Z
```

Both query params optional + independent. Inverted window
(until<since) → 400. Both zero → equivalent to ListBySchedule.
Currently mutually-exclusive with ?before= cursor (when
since/until set, before is ignored). A future cycle can add
both-at-once paging within a window.

## Store

  - New `Store.ListByScheduleRange(ctx, scheduleID, since,
    until, limit)`.
  - **Memory**: append-filtered walk; same newest-first.
  - **PG**: dynamic SQL composes `WHERE ... AND created_at
    >= $N AND created_at <= $M` so all 4 cases (both /
    since-only / until-only / none) hit the v1.92 partial
    index.
  - **BroadcastingStore**: passthrough.

## Handler

`parseRunsTimeWindow(r)` reads both query params via
shared `parseOptionalRFC3339`. Inverted ranges rejected at
parse time.

`listScheduleRuns` dispatches: when time-window set →
`ListByScheduleRange`; else → existing `ListByScheduleBefore`
cursor path (back-compat with v2.0 pagination).
